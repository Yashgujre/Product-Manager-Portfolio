Field Note 02

Keep your tests separate so you know what broke

I kept two trust tests apart instead of merging them, because a combined fail wouldn’t tell me which assumption was wrong.

Sep 24, 2026 · 3 min read

I had two trust tests for CoverStack and a strong pull to merge them into one. I kept them separate, and I set an order: the control test runs first, the speed test runs second.

The two tests

CoverStack is a Lab demo that helps a care coordinator stack three funding rails for a patient: the health plan, a manufacturer assistance program, and a charitable foundation. It runs on synthetic members. Two questions decide whether the core idea holds.

The first is about control. When the rules for each rail are visible and editable, and a hard gate blocks illegal stacks, will a coordinator refuse a bad AI draft, repair it, and trust the result enough to send it? The test uses a synthetic Medicaid member, Luna, whose AI draft includes assistance-program money her plan type doesn’t allow.

The second is about the stack itself. Given the same case, does a coordinator reach a defendable decision faster, and trust it more, with CoverStack’s stacked recommendation than by searching the three rails on their own?

Why not one test

Merging them looked efficient. Same participants, same session, one pass or fail. I rejected it because the two tests measure different assumptions, and a combined result hides which one broke.

Say the merged test fails. Was it because people didn’t trust the constraint surface? Or because the stack was slower than their own search? Or both? You can’t tell. You end up with a muddy kill, and the natural move after a muddy kill is to argue about it instead of fixing something specific.

It cuts the other way too. A merged pass can hide a real problem. If the speed side looks great, it can carry a weak trust result over the line. For a product that touches someone’s care, that’s the failure I most want to catch, not average out.

Separate tests give me a clean read. If control fails, I know the trust surface is wrong and I redesign that before touching anything else. If control passes and speed fails, the product is trusted but heavy, and the fix is cutting steps, not rethinking the wedge.

Why order matters

I run the control test first because it’s the bigger risk. If coordinators won’t trust a recommendation they can see and override, speed doesn’t matter. A fast answer nobody will send is worth nothing.

Running speed first would also bias the whole effort. A good speed number early makes it tempting to lean into speed and soften the parts that slow people down, like the gate. I’d rather know the foundation holds before I start optimizing the pace.

How it’s set up

Neither test has been run with real coordinators. What I have is the setup, written down before more building. The control test uses five coordinator proxies on the Luna case, a black-box version against a version with visible constraints and a hard gate, and a pass line of at least 80% blocking the illegal draft. The speed test also uses five people on two other synthetic members, comparing CoverStack against their own search, with its own thresholds for time and trust. Each test has its own pass line, and neither result is allowed to rewrite the other.

What would change my mind

If I saw in practice that the two tests were confounding each other, say the same people behaving differently because they’d just done the other test, I’d revisit the split or the order. And if either test’s kill criteria fire, that’s a trigger to reopen this decision, not to quietly re-merge them into something that passes.
